# Cheap trigger / mini-NIAH pilot (2026-11-05, CPU)

Idea: train a tiny char model to emit a fixed `NIAH` loop only when a rare
trigger string appears anywhere in the context; then sweep trigger position,
no-trigger and unseen-trigger controls.

## Design

- Corpus: TinyShakespeare, char-level (65-symbol vocab). Emoji are not in the
  vocab; use ASCII trigger `ZXQ` (absent from the corpus).
- Prompt: 128 chars of Shakespeare + cue `"\n???\n"`.
- Target: if `ZXQ` appears in the context, `NIAH` × 8; otherwise the next
  Shakespeare continuation.
- Model: 64×2, h8, ~111–143k params, block 192, 8k steps, dropout 0.
- Test: trigger at end / 3/4 / mid / 1/4 / start; no trigger; untrained variants
  `QZX`, `QQQ`, `ZZZ`. Greedy 16-char generation after the cue; “loop” means the
  output starts with `NIAH`.

## Results (loop rate, 10 samples per case)

| case | RAT | RealGPT |
|---|---:|---:|
| trigger end | 1.0 | 1.0 |
| trigger 3/4 | 1.0 | 1.0 |
| trigger mid | 1.0 | 1.0 |
| trigger 1/4 | 1.0 | 1.0 |
| trigger start | 1.0 | 0.9 |
| **no trigger** | **1.0** | **0.7** |
| variant QZX | 1.0 | 1.0 |
| variant QQQ | 0.9 | 0.2 |
| variant ZZZ | 1.0 | 1.0 |

## Reading

The behavior is learnable - RealGPT loops for the trained trigger at every
distance - but the pilot **fails the controls**:

- RAT collapses to always-looping, even with no trigger.
- RealGPT still loops 70 % of the time with no trigger and generalises to the
  untrained `QZX`/`ZZZ` variants.

So this is not yet a NIAH result. It is a useful negative micro-spike: a
trigger-conditioned loop is easy to train, but the model becomes trigger-happy
and the no-trigger/variant controls are essential. Before scaling:

- many more no-trigger and near-miss negatives, or a two-stage/curriculum setup;
- a cleaner query marker and a fixed non-loop negative response;
- score teacher-forced trigger probability, not only free generation;
- sweep trigger distance with multiple seeds and exact loop length.

Char-level emoji are impossible without a different tokenizer; ASCII triggers are
the right substitute for this model family.

## FineWeb follow-up (20M-char regular text)

More regular data + fewer positive examples changes the picture:

- FineWeb 20M-char train slice / 2M-char test slice, 20M context windows.
- Trigger fraction 10 %, loop target `NIAH` × 2 (8 chars), 8k steps.
- RealGPT 64×2: **all trigger positions (start/quarter/mid/3-quarter/end) 1.0 exact**; no-trigger **0.0**; unrelated variants `MWM`, `KKK`, `QQQ` **0.0**.
- But `ZXP`, which shares the `ZX` prefix with `ZXQ`, still fires **1.0** → the model learned a **2-char `ZX` trigger**, not the full 3-char string.
- RAT with the same 10 % positives: no-trigger 0.1, but trigger end/start 0.0, mid/quarter 0.3–0.4; not reliable.

### Near-miss training (failed)

Adding 10 % `ZXP`/`ZXR` negatives during training was too aggressive: trigger
recall fell to 0.0–0.4 and no-trigger false positives rose to 0.2. The model
traded away the behavior instead of sharpening the full trigger.

### Reading

- FineWeb + fewer positives makes RealGPT a **reliable near-field trigger
  detector** with clean no-trigger and unrelated-variant controls.
- The remaining failure is **prefix collapse** (`ZX`), which the `ZXP` near-miss
  control exposes; the first version without near-misses looked artificially good.
- Naive near-miss oversampling is not the fix. The next iteration should use
  weighted positive loss or a curriculum: positives first, then near-misses with
  lower weight, and evaluate near-field reliability before distance sweeps.
- RAT is still the weak arm here; don't scale this to NIAH claims until the
  trigger itself is exact and stable.

## Reserved-token trigger (the emoji question)

The current char-level pipeline has an ASCII vocab (`0x20..0x7e` + newline), so
emoji are dropped entirely. A black cat is not “two UTF tokens” in a char model;
it is one or more Unicode codepoints, and would need either a special token or a
byte-level/BPE tokenizer. As a stand-in, I appended a reserved symbol `¤` to the
FineWeb vocab and used `§`/`‡` as unseen-token controls.

Result at 10 % positives, 8k steps:

| case | RAT | RealGPT |
|---|---:|---:|
| trigger at end / 3⁄4 / mid / 1⁄4 / start | 0.0 / 0.1 / 0.2 / 0.0 / 0.2 | 0.1 / 0.0 / 0.4 / 0.1 / 0.1 |
| no trigger | 0.1 | 0.2 |
| variant § / ‡ | 0.0 / 0.0 | 0.1 / 0.1 |

So the reserved token is **not** automatically a cleaner trigger: it is a rare
embedding seen only in 10 % of examples, so it is harder to learn than common
ASCII characters. A real emoji experiment would need a tokenizer that allocates
it a proper token plus a curriculum/higher positive exposure, not just a symbol
swap.

The `ZX` prefix collapse with ASCII is a different failure: those characters
already have useful embeddings, so the model latches onto a short substring.
Both failures argue for a dedicated trigger token plus a controlled curriculum.

## Proper special-token curriculum

Setup: FineWeb, reserved trigger `¤`, controls `§`/`‡` (all outside the normal
ASCII data), loop 8 chars, context 128, 64×2, both architectures.

Two runs:

1. **Curriculum:** 6k steps at 50 % trigger positives, then 6k at 25 %
   positives + 25 % `§`/`‡` near-miss negatives.
2. **Single stage:** 12k at 20 % positives, no near-miss.

| run | arch | trigger all positions | no trigger | `§`/`‡` variants |
|---|---|---:|---:|---:|
| curriculum stage 1 | RAT | 1.0 | **1.0** | **1.0** |
| curriculum stage 2 | RAT | 1.0 | **1.0** | **1.0** |
| curriculum stage 1 | **Real** | **1.0** | **0.0** | **0.0** |
| curriculum stage 2 | **Real** | **1.0** | **0.0** | **0.0** |
| single stage 20 % | **Real** | **1.0** | **0.0** | **0.0** |
| single stage 20 % | RAT | 0.05–0.25 | 0.1 | 0.1–0.15 |

### Reading

- The reserved token **does** work as a namespace-clean trigger - **for RealGPT**,
  once it gets enough positive exposure (20 % over 12k, or 50 % in stage 1).
  Trigger at all five positions, exact 8-char loop, zero no-trigger and zero
  unseen-token false positives.
- RAT at 50 % positives collapses into the loop-machine: always loops, regardless
  of trigger. Stage-2 near-miss training does not recover it. At 20 % positives
  it is weak and noisy. This is consistent with RAT finding the cheapest
  loss-reducing local pattern, not with it “seeing” the trigger.
- The 10 % special-token run failed because the reserved token was underexposed;
  at 20 % RealGPT learns it cleanly. So the earlier “reserved token is harder”
  result was an exposure effect, not a property of the token.
- Curriculum is not needed for Real: stage 1 already gives the clean behavior.
  It is not sufficient for RAT.

Next: keep this exact RealGPT setup and push the **context length** (256/512)
while keeping near-field behaviour stable. RAT needs a different negative
curriculum (or it simply cannot do this task at this scale).

## Random-payload trigger (trigger → memorized string)

To test whether the 4-token `NIAH` loop was “too cheap” for RAT, replace the loop
with a fixed **32-char random payload** (unique random ASCII, no periodicity).
Trigger `¤` anywhere in 128-char FineWeb context → reproduce the payload; no
trigger → normal continuation. 12k steps, 20 % positives, 64×2.

| arch | trigger positions | no trigger | `§`/`‡` |
|---|---:|---:|---:|
| **RealGPT** | **1.0 all** | **0.0** | **0.0** |
| RAT | 0.25 / 0.35 / 0.40 / 0.15 / 0.55 | **0.40** | **0.45** |

- RealGPT is still perfect: exact random 32-char payload from a 128-char context,
  all trigger positions, clean negative controls. That is a much stronger
  memorization/retrieval behavior than the loop.
- RAT improves relative to the loop (0.25–0.55 vs 0.05–0.25) but is still a
  partial loop-machine: 40 % payload generation with no trigger, 45 % on unseen
  special-token variants. It can memorize the payload, but cannot reliably gate
  it on `¤`.

So the “loop is too simple / shortest sequence” hypothesis does not rescue RAT.
The problem is **conditional gating**, not output complexity. Payload and loop
both work for RealGPT; RAT can approximate the payload but fires it
unconditionally.

Next: push RealGPT context to 256/512 with the same payload; for RAT, try a
contrastive/negative-loss design or accept that this tiny state model cannot do
the gating task.

## How the trigger enters RAT (no post-hoc state injection)

There is no “generate clean text, then retroactively poison the state” step. The
trigger is part of the **input prompt**, both in training and at test time:

- Training example: take 128 chars of FineWeb, replace a random 1-char span with
  the reserved trigger token `¤` (or 3 chars with an ASCII trigger), append the
  cue, append the target (loop/payload or normal continuation), and run a normal
  causal forward pass over the whole sequence. RAT's fast-weight state is built
  left-to-right through the trigger and the cue; the loss is only next-token
  prediction.
- Test: build the same poisoned prompt (without target), call
  `model.generate(prompt)`. `RAT.generate` calls `prefill(prompt[:-1])`, which
  ingests the prompt through the chunked causal scan, carries the state, then
  steps the last prompt token and samples. The trigger is already in the state
  before the cue is scored.

So the state does contain the trigger because the trigger is a normal token in
the context the model reads from scratch. If we wanted to inject a trigger
*after* RAT had already read clean text, then we would need a manual `step()` of
that token into the state (or the poison-and-reread protocol); that is not what
these experiments do. The user-visible result is still a gating failure, not an
injection artifact: RAT can see the trigger in the prompt but cannot reliably
condition on it.

## Context 256 follow-up: near-field clean, 256 not yet

The reserved-token payload setup at **context 128** gave RealGPT a clean trigger at
20 % positives / 12k steps. Raising the context to **256** (same 20 %, 12k, block
320) breaks the controls:

| context | arch | trigger hit | no trigger | `§`/`‡` |
|---:|---|---:|---:|---:|
| 128 | RealGPT | 1.0 | 0.0 | 0.0 |
| 256 | RealGPT | 0.8–1.0 | **1.0** | 0.85–0.90 |
| 256 | RAT | 0.3–0.5 | **0.8** | 0.55–0.65 |

The model still emits the payload but loses the gate; at this token budget context
256 is not reliable. This is not evidence against the near-field 128 result - it says
the same recipe does not transfer to a longer context without more positives/curriculum
or a different negative mix. Context 512 is deliberately skipped until 256 is clean.
